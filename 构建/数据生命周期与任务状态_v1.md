# 师伴数据生命周期与任务状态规范 v1

**适用范围：** 工作区 `data/shiban/` 中的原始材料与运行时产物。此规范不改变 `services/shiban_store.py`、SQLite schema 或 `~/.shiban/data` 的持久化机制。

## 1. 数据分层

| 层 | 内容 | 规则 | 默认读取方式 |
|---|---|---|---|
| L0 原始材料 | 原始课堂记录、微格转写、教师笔记、同伴观察 | 尽量完整保存于 `data/shiban/raw/`；不压缩、不覆盖；修订另存并标明来源关系 | 默认不读全文；只有具体回溯需要时按引用读取 |
| L1 进行中工作 | 教案、随堂测、单次评价、微格评价、任务计划等详版 | 文件路径稳定；顶层 `meta.status` 记录生命周期状态；保留过程所需细节 | 当前任务直接读取 |
| L2 历史连接 | 归档索引与成长趋势摘要 | `*.index.json`；保存关键结论、趋势、日期、证据引用和数据缺口，不复制 L0 或整份 L1 | 查询、纵向汇总默认先读 L2 |

已有 JSON 若尚无 `meta`，仅在下一次正常写入时补齐，不要求批量改写既存数据。不要把 SQLite 行、日志或跨会话存储混同为本工作区 L2。

## 2. 生命周期状态

任务状态建议取值：`进行中`、`已完成`、`已归档`、`blocked`。轨道状态可额外使用 `pending`。完成表示当前目标产物齐备；归档表示已生成 L2 索引并完成引用核对。阻塞必须附具体原因，不得用“已归档”掩盖未完成工作。

- 创建多轨、分段、需要跨会话续接的任务时，创建 `data/shiban/task_plan.json`。简单单轮任务不强制建任务计划。
- 任务计划顶层与每条轨道均有状态；更新时同步 `updated_at`、产物路径和变更说明。
- 用户改变目标时先更新组织图，再继续工作；不静默丢弃旧轨道。

## 3. 归档流程

1. 核对 L1 产物与所引用 L0 文件存在，检查日期、主题、来源和关键结论。
2. 新建轻量 L2 索引，引用相对工作区路径或稳定记录 ID；保留数据缺口与置信边界。
3. 将对应 L1 `meta.status` 更新为 `已归档`，路径不变、详版不删。
4. 将 L2 索引状态标记为 `已归档`，更新 task plan 的任务/轨道状态并核对所有路径。
5. 若任何保存或引用核对失败，不得宣称归档完成，保持 `进行中` 或标为 `blocked` 并说明原因。

示例索引：

```json
{
  "schema_version": "1.0",
  "record_id": "eval-2026-07-08-dna",
  "status": "已归档",
  "kind": "class_eval|microeval|growth_report",
  "date": "2026-07-08",
  "topic": "DNA的复制",
  "raw_refs": ["data/shiban/raw/class_record_20260708.md"],
  "detail_refs": ["data/shiban/last_eval.json"],
  "key_conclusions": [],
  "trend_tags": [],
  "evidence_gaps": []
}
```

## 4. 安全边界与本轮范围

- L0 不可被 AI 整理、覆盖或删除；AI 只能建议重复项或提出另存方案。
- 归档不等于清理。未经明确授权不删除任何 L0/L1。
- 报告先读 L2，证据不足再沿引用回读 L1/L0，避免默认加载大量原文。
- 本规范是当前工作区协作约定，不自动提供文件写权限、备份能力、事务一致性或跨工作区同步。
- `services/*.py`、数据库迁移、Windows 脚本及跨会话持久化实现不在 v0.4.0 本轮施工范围。
